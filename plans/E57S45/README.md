## 四项问题的修正

| 问题                                  | 当前处理                                                                                                                                                  |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 矿箱与 Link 的拆建冲突                | 明确保留蓝图中的两个矿区 Container。矿工尊重显式规划，不再因 Link 出现而拆箱；Link 暂满时可将能量转入矿箱                                                 |
| 实际 Link 调度不优先 Storage          | 核心 Link 先接矿区输出；核心无法接纳或已接收后，余量和核心已有能量可供其他接收端。尊重 cooldown、可用容量和失败返回，同一个接收端每 tick 最多接受一次发送 |
| Queen 被 800 容量的 Link 限制单趟载量 | 优先从足够充满剩余 Carry 的孵化区 Container 取能；其次使用能填满本趟的 Link。两者不足时使用现有的较大部分载量，不等待满箱                                 |
| 道路复用不足                          | 取消对每条主路线具体道路格的锁定，合并等长通道。道路从 v3 的 166 减到 **135**，保留源2平直主路、各主路线最短步数、各 RCL 服务距离和最差补给模型表现       |

三个运行策略通过 `roomPlanner.memory.logisticsPolicy` 启用，仅 E57S45 的定制模板自动设置；其他殖民地继续沿用既有策略。

## 矿区运输与道路

| 起点                   | 到首个 Spawn | 到 Storage | 到控制器补给 Container |
| ---------------------- | -----------: | ---------: | ---------------------: |
| 北矿 Container (23,20) |            9 |         11 |                     25 |
| 西矿 Container (4,30)  |           22 |         20 |                     34 |

八方向步行，起点为矿区 Container，终点为目标建筑邻格。这六条路线达到当前固定建筑坐标与工作位约束下的最短可走格数。Storage 到控制器补给区为 13 步；不将模型步数冒充实际游戏耗时。

源2到 Storage 沿 y=30 从 (4,30) 向东至 (21,30)，再经 (22,31)、(23,32) 到邻格 (24,33)：20 步、1 次转弯。到 Spawn 为 22 步、2 次转弯。去 Spawn 末端需要避开核心建筑，不再从西侧上拱到 y=24。

v3 把每条路线的平直程度置于复用之前，且裁剪时锁定全部主路具体格子，导致 166 格道路。v4 只固定源2到 Storage、Spawn 两条平直通道；其他路线可在合并路网上重新寻路。删除路格前同时检查 14 条主路线距离、RCL2–8 各建筑服务距离和各级最差补给模型，任意一项退化就拒绝删除。

比较正向坐标、反向坐标、低复用优先、外侧优先四种裁剪顺序，均得到 **135 格**，比 v3 少 31 格（18.7%），比最初 129 格多 6 格。14 条主路线的总步数仍是 258；总转弯数为 58（最初 87、v3 为 52）。源2到控制器由 7 次转弯减为 4 次；部分其他路线增加转弯以共享通道，步数不增加。转弯数不作为移动 tick 收益计算。

重复裁剪没有进一步可删除的单格道路。这是固定建筑、源2平直通道及上述效率约束下的局部结果，不是全局最少铺路证明。建筑坐标、38 格外围防线与三处门位保持不变。共享道路可能增加实际拥堵，离线模型未模拟该项；上线前后应结合真实流量评估。源码与审查数据见 `scripts/e57s45_routes.py` 和 [routing-review.json](routing-review.json)，[optimization.json](optimization.json) 仍仅记录最初建筑候选搜索。

沿用一只移动 Queen，比较过 40 个建筑候选（24 个通过约束）与 8 种建设顺序。Extension 在预留双矿主通道后布置，优先建设靠近补给点的部分。永久建筑与原先确认的 v2 坐标保持一致。

模型从空的 Spawn、Extension 开始，采用合法 Carry 容量、道路移动、每 tick 一次转移或取能，并测试正反两种目标顺序。假设 Container 和 Link 持续有能量；它不模拟堵车、并发孵化或缺能。在 v3 中，即使孵化区 Link 有能量，充足的 Container 仍能让 Queen 一次取满，不再被限制在 800 能量的单趟载量。缺能回退通过实际 Queen 方法的回归测试覆盖。

以上为离线比较，不是上线实测或全局最高补给效率证明；多个固定 Fast Filler 属于不同的兵力、CPU 和控制逻辑方案，本次未引入。

## Link 建设顺序

1. **RCL5：核心 Link (27,31) ＋ 西矿 Link (5,29)**，先打通较远矿区与 Storage 之间的通道。
2. **RCL6：北矿 Link (24,20)**，完成双矿汇入核心。
3. **RCL7：控制器 Link (40,43)**，利用核心余量或无法接纳的矿区输出补充升级。
4. **RCL8：孵化区 Link (29,30)**，作为缓冲补给和缺能回退；Queen 优先从充足 Container 取能。

最终保留一个 Link 名额。这里的 Storage 优先指 Storage 旁核心 Link 的接收优先；它也能用已有能量向控制器等接收端转发，避免其他节点永久饥饿，并非要求每单位能量都先进入 Storage 再取出。

## 本地接入与验证

`src/roomPlanner/layouts/E57S45.ts` 从蓝图生成，`roomOverrides.ts` 仅在 shard3 的 E57S45 已归我方所有后安装，并随 RCL 更新分级道路、防线及运行策略。安装函数不会创建旗帜或执行占领。用户后续授权殖民后，已部署 main 并创建独立殖民指令；占领后模板自动接管分级建设。

```sh
python3 scripts/plan-e57s45.py --check
python3 scripts/test_e57s45_routes.py
npm test
npm run check
```

`--check` 同时核对蓝图、路线审查、SVG 与运行时代码是否可复现。`--optimize` 可以重新比较建筑候选，属于重新规划；目前已确认的坐标无需重选。殖民前已重新核对目标归属、GCL 名额、母城资源和补给路径，结果记录于执行记录。
